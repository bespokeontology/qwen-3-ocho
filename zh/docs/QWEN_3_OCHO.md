# Qwen 3.ocho (C++) —— 原生 CUDA/HIP/ROCm 推理引擎（NVIDIA GB10 + 4x AMD MI50）上的随机轨迹渲染与决策/提交循环

状态：2026-09-07 能力边界。本文记录的是一个已工作的机制，不是基准测试结果。所有数字均为当晚
在现有硬件上的实测值；节点热/功耗限制在相关处如实注明。

原生吞吐参考：本引擎在此硬件（一台 DGX Spark（GB10）尾部 + 4x AMD MI50 前缀）上的 M=1 解码路径，
在 8K 生产配方、无投机解码的条件下实测为 27–29 tok/s（取自规范隔夜冻结的各收据运行）。Qwen
3.ocho 的随机模式与该路径并行存在；其逐行渲染成本单独列于下文，并非原生路径的替代。

## 1. 是什么

Qwen 3.Ocho 是原生引擎（4x AMD MI50 前缀 + NVIDIA GB10 尾部，架构见 ARCHITECTURE.md）的一种
运行模式：对同一份常驻模型状态渲染多条随机延续，既可把它们作为并行未来直接返回（Beam），也可反复
评估并把其中一条提交进常驻状态后继续（Loop）。

两种一等模式：

- **Ocho Beam**：一份常驻父状态分叉为八条替代未来，各自独立渲染指定步数。未来本身即输出。
- **Ocho Loop**：渲染八条未来 -> 评估 -> 选择 -> 把所选后果提交进常驻状态 -> 从该因果状态继续 ->
  渲染下一批八条未来。

## 2. 机制

常驻父状态是提示词预填后的 M=1 状态：两侧加速器上的 KV [0,P)、循环（GDN）状态、卷积环、索引池与
PLE 历史。分叉操作把该状态复制到两侧的八个行槽位（AMD 前缀层与 Spark 尾层）。第 0 行保持贪婪
argmax；第 1–7 行按逐行 Gumbel-max 噪声从头层 logits 采样，给定种子下完全确定：

    sample_v = argmax_v ( logit_v / T - log(-log(u_v)) ),  u_v = splitmix64(seed ^ (r<<40) ^ v)

其中 v 为词表下标。八行经 M 行区域路径（AMD 前缀 -> Spark 尾部 -> AMD 头部）逐步同步推进；线上只
传输 token id。

Loop 的评估阶段刻意保持简单并全程留痕：早停（early EOS）与尾部词表伪影 token（实测乱码簇位于
token id >= 110000）被记罚；剩余分数为各行循环状态签名（sigR：Spark 层 GDN 与卷积状态之和）距
字段中位数的距离。按词典序得分最优的行被提交：其完整状态（KV、循环状态、索引池、PLE 历史）在两侧
复制回父槽位，下一轮迭代从该状态重新分叉。条件概率树保留在运行日志中：每条分支的 token、签名、
得分与每一次选择。

弃枝上下文继承（概念验证）：每轮提交后，将落选分支在主机侧解码并分类为约束 / 失败 / 未决问题命题
（泛泛复述被拒绝）；每轮取一条命题，上限 64 token，以 [OCHO BRANCH MEMORY] 块经已验证的常驻再填充
路径注入已提交的冠军。落选行的 KV/状态绝不合并。冻结：FREEZE_OCHO_BRANCHMEMORY_POC_20260907。

字段同一性不变式：相同父状态、种子与分叉请求产生相同的八路字段，与服务器此前服务过什么无关。为此
需要在分叉/重置边界复位头部采样器的进程级调用计数器（见第 4 节）。

## 3. 实测行为

| 配置 | 测量值 |
|---|---|
| K=16 字段，8 行，编程任务提示 | 5.16 s；322.7 ms/步；24.8 sibling-tok/s（每行 3.10） |
| K=1500 Beam，C++ 任务 | 851.7 s；567.8 ms/步；14.1 sibling-tok/s |
| K=1500 Beam，Rust 任务 | 845.6 s；563.7 ms/步；14.2 sibling-tok/s |
| Ocho Loop，K=48 x 16 轮，C++ 任务 | 768 个提交 token；每轮渲染+提交约 24 s；干净退出 |
| Ocho Loop，K=48 x 16 轮，Rust 任务 | 768 个提交 token；每轮约 20-25 s；干净退出；选择器在六行间切换 |
| 受限候选采样器（服务端 7c677e80），K=16 字段 | 311.9 ms/步（全词表时 324.6）；K=128 Beam 中零非 ASCII 乱码 |
| 同进程字段同一性门（K=16 连跑两次） | 八行字段逐位一致 |

K=128 时八条未来是可读的工程推理（对 MPMC 队列任务全部收敛到互斥锁 + 双条件变量；其中一条分支跳过
推理块直接开始写代码）。K=1500 时每条温度 1.0 采样行都累积乱码伪影（词表尾部的西里尔/阿拉伯/中日韩
片段），而贪婪行保持干净。Loop 的 768 token 提交轨迹是连续的工程设计推理：环形缓冲 + 双条件变量、
跨迭代反复审视 close() 的“排空 vs 立即失败”歧义、以及丢失唤醒的谓词分析。当前过滤器在 768 个提交
token 中漏过 3 个伪影 token（约 0.4%）。

## 4. 为达到该能力所做的修复

- **字段同一性（服务端）**：AMD 头部的 Gumbel 种子带有一个进程级调用计数器偏移，导致复用服务器对
  相同请求产生不同字段。修复：在 REGION_FORK/REGION_RESET 复位计数器；以上述同进程门验证。
- **循环累积（客户端）**：分块渲染按“块长”步幅写行，而选择器按 K 步幅读。修复：每块临时缓冲并拷入
  K 步幅轨迹。块边界只是观察点；选择器看到的 K 个 token 与一次性调用完全相同。
- **选择器死锁**：当每行都带伪影时，初版选择器排除全部行导致无从提交。现行选择器总是会选：伪影最少
  者优先，早停重罚，共识距离次之。

## 5. 已知限制

- 区域线路上只传 token id、不传 logits：没有逐行对数概率，加权蒙特卡洛积分需要 logits 扩展。
- 伪影过滤器是主机侧 id 阈值判别器，不是词表感知分类器；在 id 110000 以下存在漏报。
- 受限候选采样现已保留（服务端 7c677e80，收据 SAMPLER_TOPK_RECEIPT_20260907）：每线程前 8 候选、
  在 2048 候选集上做 Gumbel-max，第 0 行全词表 argmax 逐位一致，实测的尾部词表文本污染在采样器
  层面被消除。全扫描经 QF_HEAD_FULLSCAN=1 仍可用。循环选择器的 id 阈值过滤器保留为后备。
- M=8 是已验证的分叉宽度；M=16 状态路径需要独立的正确性回合。
- QF_HEAD_TEMP 与 QF_HEAD_SEED 在服务端启动时读取一次：每次启动一个种子。
- 测量于约 220 W 功耗上限、且有不稳定历史（传动系亏缺失效模式）的 Spark 节点；计划更换为 Atlas
  300I，预期更适合该负载。计时数字应视为节点特定。

## 6. 冻结产物

FREEZE_OCHO_20260907（行为证据：K=128 与 K=1500 Beam、一致性门、字段同一性泄漏复现）与
FREEZE_OCHO_CAPABILITY_20260907（可工作的 Loop：二进制、源码、门日志、16 轮运行与提交轨迹）、
FREEZE_OCHO_RUST_LOOP_20260907（第二份能力轨迹，Rust 任务）与 FREEZE_OCHO_TOPKSAMPLER_20260907
（保留的受限候选采样器：二进制、源码、门与 K=128 Beam 对比）。
两者均经 SHA256 校验并镜像。Loop 客户端位于分支 stoch-engine-0907（提交 257a2a1）；带提交操作的
AMD 服务端由归档的 pre-B3 分叉树加 QFW_REGION_COMMIT 操作与字段同一性复位构建。
